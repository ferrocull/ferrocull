# Durable culling state is keyed by the ingest fingerprint

Tag, rating, and color label are persisted against the ingest fingerprint (basename, file size, capture time), the same identity the ingest history uses to answer "have I ingested this frame before". The canonical path is not part of the key: a path describes where a frame currently sits, not which frame it is.

The decisive argument is lifecycle, not collision probability. A tag lives until its frame is ingested, and ingest records that fact under the fingerprint. Keying the tag by path would give its birth and its death two different keys: a frame tagged under one mount point and ingested under another leaves an orphaned row that later resurrects the tag on a frame that already reads as ingested. Sharing one key makes that state unrepresentable rather than merely unlikely.

Rejected: keying by canonical path. Paths are facts about a mount point, not about frames. Two cards from the same camera body carry the same factory volume label and swap mount directories with insertion order; Windows reassigns removable drive letters whenever another device claims one first. The path-keyed catalogs (Lightroom Classic, darktable) are precisely the tools with documented "photos missing after drive letter change" failure modes and manual relink flows. Rapid Photo Downloader, the closest comparable workflow, keys its downloaded table on basename, size, and mtime with no path and no volume identifier; the fingerprint is that scheme with EXIF capture time in place of mtime, which does not drift with timezone and DST the way FAT mtime does.

Rejected: volume UUID plus relative path, the digiKam model. It survives remounts but dies on reformat, which photographers do routinely to cards, so for card culling it is strictly worse than the fingerprint while costing more machinery.

The costs: identity detaches when a file is renamed or edited in place, since basename and size are components of the key. That is immaterial for camera cards, where originals are immutable, and relevant only for Directory sources holding files someone edits. Two genuinely distinct frames sharing basename, byte size, and capture time to the subsecond share culling state; the realistic exposure is files with no capture metadata, where capture time falls back to mtime. The ingest history already accepts that identical risk with a worse consequence (a collision there silently hides a new frame behind the new-only filter), whereas shared culling state is visible in the grid and corrected with one keystroke. And loading both a card and a copy of that card as sources simultaneously shows the same frame twice sharing one tagged state, a rare setup whose rename pattern would already collide at the ingest destination independently of tagging.

This is the same path-versus-content choice as the [content-based thumbnail cache key](0005-content-based-cache-keys.md), one level down: the cache identifies bytes by their hash so a remount preserves thumbnails; the metadata store identifies frames by their fingerprint so a remount preserves culling work. Path canonicalization survives only to feed the cache key; a path is no longer an identity anywhere.
